Detailed Description

A build backend: everything the editor knows about one kind of target.

One implementation per build framework - a microcontroller SDK, the desktop the editor runs on, an app format for someone else's firmware, a console SDK. It generates the target's build files, drives its toolchain and knows what getting a build onto a device means there.

The editor ships none. A backend arrives in a package's editor-side DLL (see BuilderPlugin.h) or as a plugin under ~/.deki-editor/builders/, so a target can be added - including one whose SDK cannot be published - without an editor release.

◆ GetFrameworkId()

virtual std::string DekiEditor::ITargetBuilder::GetFrameworkId ( ) const
pure virtual

The build framework this backend serves, as a lowercase id.

THE dispatch key: a platform names its framework and the registry hands it to whoever claims that id.

Not the vendor family, which cannot distinguish two backends for the same silicon: an app format that runs on a chip and that chip's own SDK share a family and must not share a build. Not GetPlatformKey() either, which reads the platform config this builder was already given and so cannot be used to choose it.

◆ GetBootPayloadDirectory()

virtual std::string DekiEditor::ITargetBuilder::GetBootPayloadDirectory ( const std::string & projectPath) const
pure virtual

Where the editor writes the boot payload before Build(): the compiled project settings (dproject.bin) and the platform's boot scene.

What becomes of the directory is the backend's business - packed into a flash filesystem image, copied beside an executable, bundled into an app archive. Empty means this target takes no boot payload, and the editor writes none.

Pure on purpose. The editor used to decide this itself, as "<build directory>/spiffs_data" - one target's partition name, which every backend then had to know to look for.
