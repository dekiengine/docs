◆ AssetCacheHandler

using DekiEditor::AssetCacheHandler = std::function<AssetCacheResult(const AssetCacheContext& ctx)>

Asset cache handler callback type.

Called during ProcessAsset for registered extensions. Responsible for generating cache files and registering sub-assets. Returns an AssetCacheResult describing what happened (see enum above).

Packages can register handlers via AssetPipeline::OnStarted to override built-in handlers or add support for new file types.

◆ ParseBuilderDefinition()

bool DekiEditor::ParseBuilderDefinition ( const std::string & jsonText,
BuilderDefinition & outDef,
std::string & outError )

Parse a toolchain definition from JSON text.

Text, not a path, is the primary form: a build backend lives in a package, and the package DLL is built into the project's runtime directory, nowhere near its own sources - so a backend carries its definition inside itself rather than hoping a file sits beside the editor. It used to: the ESP-IDF backend read resources/builders/espidf.json next to DekiEditor.exe, which made the editor ship one framework's recipe after the backend had left.

A failure says why in outError. There is no silent "no toolchain" state.

◆ NormalizeProjectRoot()

std::string DekiEditor::NormalizeProjectRoot ( const std::string & projectPath)
inline

Where a project's generated content lives.

This is the public, package-visible definition of the layout, and the only one. src/core/ProjectPaths.h delegates here rather than restating it — an earlier split between the two is exactly how cache/ ended up being recreated at the project root after everything else had moved under generated/.

Header-only and dependency-free so a package can include it without linking anything.

Normalise a project root to an absolute path.

Every path below is built on this. A relative project root is not merely untidy: package DLLs are loaded with LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR, which rejects a relative path outright (ERROR_INVALID_PARAMETER), so opening a project by a relative path made every package fail to load with an error that pointed at the DLL rather than the path. Resolving once, here, means no caller has to remember.

◆ RunShellCommand()

int DekiEditor::RunShellCommand ( const std::string & commandLine,
const std::string & workingDirectory,
const std::function< void(const std::string &line)> & onLine,
const std::atomic< bool > * cancel = nullptr )

Run commandLine through the platform shell: cmd.exe /S /C "<line>" on Windows, /bin/sh -c elsewhere.

stdout and stderr are merged and delivered to onLine one line at a time (no trailing newline; empty lines skipped), on the calling thread, as they arrive.

workingDirectory may be empty for the current one. When cancel becomes true the command is stopped - on Windows the whole process tree, since a build step's work happens in grandchildren (idf.py -> ninja -> compilers) - and the result is -1.

Returns the command's exit code, or -1 when it could not be started or was cancelled.

◆ CompareVersions()

int DekiEditor::CompareVersions ( const std::string & a,
const std::string & b )

Compare two dotted version strings ("3.1.1" vs "3.2.0").

Returns -1 if a < b, 0 if equal, 1 if a > b.

Missing trailing segments count as 0, so "1.1" == "1.1.0" and "1.1" < "1.1.2". Segments parse with atoi, so a trailing suffix on a segment is ignored ("1.2.0-rc1" compares equal to "1.2.0"): the package and framework manifests this reads only ever carry numeric versions.

This lived as two byte-identical static copies, in the build base class and in an installer, before the engine-version gate needed a third.
