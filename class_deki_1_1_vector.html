Detailed Description

template<typename T>
class Deki::Vector< T >

Growable array of T with failable growth.

Move-only, like Buffer, and for the same reason: copying needs a second allocation that can fail, which a copy constructor cannot report.

T must be trivially copyable and trivially destructible - the same constraint Buffer imposes, enforced by it. Growth moves elements with a memcpy and destruction frees the block, so a T with a destructor or a non-trivial move would be silently mishandled. These are the plain structs and handles device code keeps lists of.

◆ Reserve()

template<typename T>
bool Deki::Vector< T >::Reserve ( size_t count)
inline

Make room for at least count elements.

Say this once, up front, where a failure is easy to handle - then the PushBack calls that follow cannot fail. That is the pattern worth writing on a device: one check instead of one per element.

Never shrinks. Returns true when the capacity is already sufficient.

Placement comes from the constructor, so a growth inside PushBack lands in the same region as the storage it replaces.

◆ PushBack()

bool Deki::Vector< T >::PushBack ( const T & value)
inline

Append a copy of value, growing if needed.

Returns
false when it had to grow and could not; the vector is unchanged and still holds everything it did before

Growth doubles, from a first block of 4. Doubling is what keeps appending amortised O(1); the small first block is because a device project has many short lists and one 16-element default each would add up to more than the lists do.

bool Deki::Vector< T >::RemoveUnordered ( size_t index)

Remove the element at index, filling the hole with the last one.

O(1), and it does not preserve order - which is what a device wants for the lists it keeps (live entities, active timers) and is the same trick ParticlePool's KillSwap uses. For order-preserving removal, rebuild.
