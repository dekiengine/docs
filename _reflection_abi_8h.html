Bump ONLY for a layout change that keeps every sizeof identical (reordering or repurposing a field).

Size changes are caught anyway.

2: dropped sizeofNodeMeta. DekiNodeMeta moved out of the engine into the deki-nodegraph package, and the engine must not include a package header to build its own ABI fingerprint. That guard now lives where the struct does: NodeTypeRegistry::Register takes the caller's compiled sizeof through a default argument and refuses a meta that disagrees. This field shrinking is itself a layout change, hence the bump — version sits at offset 0 in both the old and new struct, so a pre-bump DLL is rejected on it.

3: added sizeofDekiObject and sizeofDekiComponent. Until now the handshake covered only the reflection tables, while packages were also reading Deki::Object's members through inline accessors with nothing checking that layout at all. Growing the struct is itself a layout change, so the bump is required: a version-2 DLL returns a shorter struct, and reading the two new fields out of it would read past its end. The loader must therefore check version THROUGH THE POINTER before copying the struct by value.

4: dropped the deprecated getType()/getBaseType() forwarders. The struct is unchanged and every sizeof still matches, so nothing else here would catch a package built against v3 – it would reference a spelling that no longer exists. This is exactly the layout-compatible but semantically incompatible case this counter exists for: bump it so such a package is refused at load rather than failing in a confusing way later.

5: added the Deki::Component::DeclaresUpdate() virtual. Every sizeof is unchanged, but a slot was inserted in the middle of the component vtable, so a package built against v4 calls the wrong function through every virtual after it (seen as an integer divide by zero deep inside a stale plugin while compiling a scene). The vtable is part of the ABI even though nothing here can measure it: any new virtual on Deki::Component or Deki::Behaviour needs a bump.

(no bump) Deki::PropertyInfo grew renamedFrom (DEKI_RENAMED_FROM). The struct's size changed, which sizeofPropertyInfo catches on its own: a package built before it is refused and rebuilt.

(no bump) Deki::PropertyInfo grew enumInts, the underlying value of each enumerator beside the existing names. Same reasoning: sizeofPropertyInfo moves, so a package built before it is refused and rebuilt rather than having its enum tables read as though a list position were a value.

6: engine 0.10 (the namespace release) moved every engine type into namespace Deki (Deki::Object -> Deki::Object, ...). Every sizeof is unchanged, but the symbol mangling of every exported engine function changed, so a 1.x package DLL would fail to load with unresolved imports; the bump turns that into the loader's "built against another engine, rebuilding" path instead.

7: engine 0.11 (macro-free components). Deki::Component lost six virtuals (GetType, GetBaseType, DeclaresUpdate, Deserialize, ResolveObjectRefs, RemapObjectRefs are now plain calls through the instance's ComponentTypeInfo pointer, which also grew the class by one pointer), and a component's identity is the hash of its qualified class name instead of a declared GUID. sizeofDekiComponent catches the size, the version bump catches the vtable.

8: engine 0.12 dropped Deki::Behaviour::NeedsUpdate() (a virtual) and its flag. Declaring Update() is the only thing that makes it run. A slot left the Behaviour vtable, so a v7 package would call the wrong function through every virtual after it.

9: engine 0.13 merged Deki::Behaviour into Deki::Component. Component gained Awake/Start/Update and two state flags, lost AsBehaviour(), and Behaviour is gone: every package rebuilds against the one base.

10: added transformConfig. The transform width became a build switch (DEKI_TRANSFORM_2D / DEKI_TRANSFORM_3D), so Deki::Object's layout is now a property of the project's configuration and the handshake has to say which one a DLL was built for. Growing the struct is itself the layout change that forces the bump.

11: Deki::IMemoryProvider gained AllocateDMA. Memory::Region::DMA promised a buffer a peripheral could read, and only the platform knows how to get one — on the ESP32 some internal RAM is not DMA-reachable, so "internal and probably fine" was silent corruption waiting for a display driver. Adding the virtual moves every slot after it, so a provider DLL built at ABI 10 would call the wrong one. No struct grew, which is exactly the case the size fingerprint cannot see and this number exists for.

12: Deki::IMemoryProvider gained AllocateRaw, FreeRaw and GetRawBlockSize, the plain natural-alignment allocator the global operator new routes through, so every allocation on a device goes through the provider without paying for a bookkeeping header. Appended, so ABI 11's slots keep their indices — but 11 was published to master for a few hours and package DLLs were built against it, and those would call into the provider past the end of the vtable they know. Two numbers inside one unreleased cycle is cheaper than one silent miscall.

13: Deki::Memory's allocating functions take a Deki::AllocContext instead of a const char*, so an allocation names itself without the caller writing a label. Nothing grew and no vtable moved — AllocContext is a single pointer in a release build, the same size the parameter always was — but the mangled names of Allocate, AllocateInternal and Free all changed, so a package DLL built at ABI 12 would not resolve them. The size fingerprint cannot see a parameter type change either, which is the second time this cycle that is the reason for a bump.

Also in 13: IMemoryProvider::AllocateDma is spelled AllocateDMA, and the placement virtuals (AllocateInternal, AllocateDMA, FreeInternal, GetAvailableInternalRAM) lost their default implementations. Neither moves a slot — a rename keeps its index and a pure virtual keeps its index — so both are source breaks rather than binary ones, and they ride along on a number this cycle had already bumped. Unlike 11, ABI 13 never reached master, so nothing was ever built against an earlier spelling of it.

AllocContext also has a different LAYOUT between debug and release: it carries file, function and line only where DEKI_ALLOC_CONTEXT_CAPTURE is defined. Mixing a debug engine with release packages was already unsupported (MemoryStats has done this for longer), and this makes the consequence sharper rather than introducing it.

14: Memory regions replace the MemoryUse enum and IMemoryProvider serves them through Allocate/Free/GetAvailable/Serves instead of a virtual per region, so a package can define a region the engine has never heard of.

15: MemoryRegion is Memory::Region, nested where it belongs.

16: IDisplay::Present and PresentRegions take a ColorFormat instead of an int whose numbering lived in a comment and as literals in every display.

17: packages moved their types into a namespace of their own, so every component is identified by a qualified name rather than a bare one and nothing of a package's sits at global scope. No layout moved, but the mangling of anything naming a package type did — IRenderSystem's SetRenderer and GetRenderer take DekiRendering::DekiRenderer now — so a package built before this fails to resolve against the engine's symbols. The bump turns that into the loader's "rebuild it" path.
