Detailed Description

Memory Provider for Deki Engine.

Provides centralized memory management with PSRAM support. Handles PSRAM usage and RAM allocation limits for the Deki.

Allocate memory a DMA engine can read, from region.

Reachability is a constraint, not a place: a framebuffer must be reachable whether the board keeps it in internal RAM or in PSRAM, and saying so with a separate entry point means neither choice can silently drop the requirement. On a platform where every allocation is equally reachable this is the same as Allocate, and the provider says so.

◆ AllocateArray()

template<typename T>
T * Deki::Memory::AllocateArray ( size_t count,
Memory::Region region,
AllocContext ctx = {} )
inlinestatic

Allocate an array of count T, or return nullptr.

Use this instead of new T[count] for anything whose size comes from a file, a scene, or the screen.

new[] cannot fail gracefully on a device: ESP-IDF builds with exceptions off, so the bad_alloc reaches __cxa_allocate_exception and calls abort(), rebooting the board. std::nothrow does not help either, because libstdc++ implements it by calling the throwing form inside a try/catch that -fno-exceptions has removed. A caller that checks the result can carry on without the thing it wanted, which is nearly always better than a reboot.

The multiplication is checked too. A count read from a file is attacker- or corruption-controlled, and count * sizeof(T) is computed in a 32-bit size_t on the device, so a large count silently wraps to a small one.

Trivially copyable only: this does not construct anything, matching the raw buffers it replaces.

◆ GetRawAllocated()

size_t Deki::Memory::GetRawAllocated ( )
static

Bytes currently held by the raw (operator new) path.

Returns
Live bytes in std::vector, std::string and scalar new allocations, or 0 when the build does not count them

Requires DEKI_MEMORY_TRACK_RAW, and returns 0 without it. Counting needs the block size on free, and with no header the only source is the heap: measured at +35% per allocation (63-71 ns against 47-52 for malloc+free), because on Windows that is _msize calling HeapSize and taking a lock. Routing itself is free, so every build routes and only a build that asks counts. Turn it on while hunting where memory went.

Approximate even then: allocations made before the memory backend exists (static initialisers) are freed through it afterwards, so the total is clamped at zero rather than allowed to underflow into a nonsense figure. It is a diagnostic, not an invariant.
